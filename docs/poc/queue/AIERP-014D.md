## 要设计的完整采购链路

用户：“帮我采购 10L 表面活性剂” → DeepSeek 提取意图 + 物料/单位/数量，查询真实 ERP 物料及仓库/供应商候选 → 缺少信息逐项追问 → Java 服务端校验授权与主数据 → **生成待确认草稿（未过账）** → 企微明确展示物料名称/编码、采购供应商、入库仓库、数量、参考价/金额与估算库存变化 → 用户明确确认 → 服务端从已绑定 ERP 用户执行原有 `purchase/draft` + `draft.confirm` → 回真实单号和库存变化。

**预览阶段可调用现有 `purchase/draft` 创建 DRAFT，但创建草稿绝不审核过账**。客户希望像正常业务一样反悔、取消、编辑草稿，需明确状态和并发规则。

## 必须论证的确认信任链

- **不能**仅让模型调 `erp_draft_confirm({draftId})` 后端就入账。模型自生成“用户已确认”字段不可信。
- 优先评估企业微信官方模板卡片按键回调的 **真实渠道事件签名、发送者及消息与草稿关联**，SDK 无法直接确认时按“带一次性挑战码的实际私聊消息事件”或“已认证 H5 页面点击确认”保底；绝对不把无法验证的普通 LLM 文本当成确实收到的点击。
- 服务端发行 5–10 分钟一次性确认挑战（绑定 `bot+wecomUser+erpUser+tenant+draftId+draftVersion+businessHash`），确认前重检绑定状态、当前角色/仓库/审批权限和主数据，哈希内容不一致必须重新确认。
- 明确草稿、待确认、确认中、已过账、取消、已过期、失败可重试、已重复确认等状态；**任何重试不产生第二张审核单**。确认成功返回原生单据号，出错不得谎称成功。
- 企业微信收发和用户双击事件可能重复；使用事务、唯一幂等键、消费回执、失败补偿、日志脱敏。对接多实例时持久化 nonce/挑战。
- OpenClaw 不暴露用户 ERP 密码/长期 Token、不得使用统一管理员会话审核他人的单据。当前 ERP 原生 `AierpGatewayService` 依赖 HTTP session，说明服务端受控委托如何严格按实际绑定用户完成原生过账，而不是通过 thread-local 猜测。
- 权限风险：供应商/客户列表是否有可见范围、同一员工是否可跨仓、禁止群聊业务写操作、失效用户/租户如何即时阻断、卡片长时间未确认如何处理。
