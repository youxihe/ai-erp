# AI-ERP · 客户演示后业务架构与 ERP 底座评估（2026-10-25）

> **权威级别：产品业务边界 / 新需求基准。** 来源是 2026-10-25 客户核心人员演示后的第一手业务反馈。客户表述的范围视为当前需求输入；具体工作流、库存计价、状态枚举和 ERP 底座选择属于**待设计/待验证**，不是已经客户确认的实现方案。此文优先于旧 POC 的“原料合成药水/MIX 是核心生产模型”假设。关联根目录 `AGENTS.md` 和 `deploy/openclaw/workspace/AGENTS.md`。

## 1. 产品定位与三层架构

这是以 **销售订单（Sales Order）作为业务主线、具备简化生产任务管理的订单驱动型轻量制造 ERP**，不是纯进销存聊天 Bot、MES 或大型 CRM/财务总账。

- **ERP 主体（PC Web + Java）**：客户、供应商、物料、订单、BOM/任务、采购、库存、交付、财务记录、权限和查询报表的权威数据与交易闭环。今后主要定制范围首先落这里；不能把生产任务“藏在 AGENT 提示词里”。
- **企业微信组织身份与 H5（第二阶段）**：基于企业微信企业组织/成员 ID 关联唯一 ERP 账号及企业/角色/数据权限；组织变动、离职、岗位变化必须有同步和撤权。自建 H5 为 PC 之外的常用业务办理入口（例如车间任务、销售报备、仓库单据），不是只通过私聊。
- **OpenClaw / 企业微信 ERP 机器人（第二阶段）**：自然语言/Excel/图片查询和高频 SOP，基于 ERP 的正式 API 与服务端角色/绑定校验，不能成为另一套业务数据库；真实写入有原文授权、幂等、审计及 PDF 操作回执。PC、H5 和机器人操作同一个流程状态。

**决定**：当前先调研并完善 ERP 核心产品与数据模型，暂停新的企微卡片/图表/H5/机器人新增任务，已验收功能保留且不破坏。**不要认为 GitHub 已有代码 = 本机已部署或业务已完备。**

## 2. 角色与本期业务边界（2026-10-25 客户输入）

| 角色 | 本期职责和核心页面 | 关键责任/约束 |
|---|---|---|
| 销售 | 客户记录/报备、创建销售订单、按订单看交付/开票/收款进度 | CRM **轻量化**：不做复杂线索漏斗、营销自动化；报备归属/查重可设规则；销售订单是全链路主键 |
| 设计 | **仅生产类订单**拆 BOM 及生产任务；任务计划开始/完成时间、负责人/车间、进度状态、实际完成时间 | 客户不是要研发复杂工艺路线/MES；支持 BOM 版本和任务责任、交期控制是最小闭环 |
| 采购 | 根据所有订单产生的物料需求（其中生产订单要先展开 BOM）查可用库存/缺口，采购申请→采购订单，登记采购发票/报销/付款材料 | 不能“所有订单都有 BOM”：耗材/零部件订单直接使用销售明细产生需求；缺口计算必须考虑已占用量与待到货，防止重复采购 |
| 仓库 | 采购到货入库；耗材/零部件订单直接领货/出库；生产领料、产成品入库、订单交付出库 | 每次库存变化必须有原生单据、仓库、订单/工单关联和审批；严禁仅任务状态改变库存 |
| 车间 | 生产类订单领料、分配的任务进度/完成情况、实际耗材、产成品入库 | 任务状态 ≠ 库存交易；是否允许部分完成/多次领料后续确认 |
| 物流 | 交付物流角色已提出，但具体职责**待客户补充** | 暂不自创复杂运输/运单/轨迹模块；可先留字段、节点和业务权限扩展点 |
| 管理 | 销售/订单统计、交付状态/预计逾期、物料成本、订单毛利（若计价真实可得） | 订单维度 Drill-down；成本没有经确认的计价口径时禁止编造数字 |
| 财务 | **轻量台账**：销售订单关联开票/收款，采购订单关联付款/采购发票/报销材料 | 不强制总账/凭证/税务申报/银行对账；保留开票额、应收已收、应付已付、附件、日期及状态；会计功能边界待客户确认 |

本期共有 **四种销售订单业务类型**，不是四个彼此独立、无关联的系统：

| 订单类型 | 交付路径 | BOM / 生产任务 | 库存动作 |
|---|---|---|---|
| **生产订单** | 销售订单 → 设计/BOM版本 → 物料缺口 → 采购/领料 → 车间任务 → 产成品入库 → 交付出库 | **需要**：仅该类型展开 BOM、拆任务并分配车间负责人、计划/实际完成时间 | 原材料入库、生产领料出库、产成品入库、交付出库 |
| **耗材订单** | 销售订单 → 查看库存/缺口 → 采购（需要时） → 直接销售出库/交付 | **不需要** | 采购入库/直接出库 |
| **零部件订单** | 销售订单 → 查看库存/缺口 → 采购（需要时） → 直接销售出库/交付 | **不需要** | 采购入库/直接出库 |
| **服务订单** | 销售订单/服务记录 → 服务执行/完成状态 → 交付记录 | **不需要** | **默认不自动扣料或自动形成销售出库**；若服务需领用耗材，应单独由用户指定并产生正式单据，待客户确认 |

**明确排除**：客户本期**不做原料合成药水/配方化学混合**。POC 既存 MIX `AierpWecomMixService` 和技能属于历史技术实验/可选保留能力，**不得再作为新产品的生产订单定义和核心 SOP**；不能把 MIX 的配方确认逻辑拿来冒充生产 BOM/工单/车间任务；无需未经确认就删除旧代码/历史单据。历史服务耗料 SERVICE POC 也不等于全部“服务订单”：SERVICE 是库存消耗单，用户新定义的服务订单只做业务记录。

## 3. 最重要的一条全程业务主线

```text
客户/销售报备
  └→ 销售订单 (orderId, orderType, owner, promisedDeliveryAt, customer)
       ├→ 耗材/零部件：明细需求 → 可用库存/缺口 → 采购（如需） → 销售出库 → 交付
       ├→ 服务：服务记录/进度 → 结单（默认无库存动作）
       └→ 生产：设计确认 → BOM（版本/生效） → 展开需料 → 库存缺口/采购
                     → 生产任务（车间负责人、计划、进度、实际完成时间）
                     → 原材料领料出库 → 产成品入库 → 发货交付
       └→ 财务轻台账：应收/开票/收款、采购发票/应付/付款；状态回流销售与管理
```

### 最小核心数据对象（建议，未落库）
- `SalesOrder` + `SalesOrderLine`，`orderType` 区分 PRODUCT/CONSUMABLE/PART/SERVICE；本期可先单类型订单，**一张销售订单是否允许不同类型行，客户待确认**。客户原文的四种叫法是业务类型，字段名只是架构建议。
- `BomHeader` + `BomLine` + BOM 版本：按产成品/订单配置，至少支持设计人、版本、状态和材料/数量/损耗（损耗算法待确认）；审批发布后保留快照，后续改版不得静默修改已领料工单。
- `ProductionOrder` 或 `ProductionTaskGroup`（生产订单执行实例）与 `ProductionTask`（岗位/负责人/车间、计划/实际起止、状态、排序、阻塞原因、完成回报）；只做轻任务跟踪，不做 MES/复杂设备产能排程。
- `OrderMaterialDemand`（来源订单行/BOM版本，需求量、已预留、已采购未到货、可用库存和缺口）与 `OrderProcurementAllocation`（一张采购单可服务多销售订单，反向可追踪），避免采购和设计重复核算。
- `OrderFulfillment` / `DeliveryRecord`（单次部分交付、已发/待发、交期），`OrderInvoiceRecord`/`OrderPaymentRecord`（票据/付款/收款台账）。
- 订单、工单、采购单、库存出入库、费用/票据和任务间需有**明确关系表/外键**，不要把 ID 塞进通用 `remark`/JSON 列或复用 unrelated native assemble field。所有状态/金额/库存有唯一权威源。

### 必须先设计的业务语义
- **订单交付状态**≠生产任务进度≠入库审核≠财务收款；必须分维度跟踪，可汇总但不得串改。
- BOM 拆需求 vs 采购执行：**可用库存 = 现存量 - 已被其他订单有效预留量**，新需采购 = max(0, 需求 - 可用 - 已确认可覆盖的在途量)，具体“在途”与安全库存口径需客户确认；本期可实现轻量预留，不必重型 MRP。
- **成本**：库存、采购订单的单价不等于生产实际物料成本；最低建立领料实际数量 × 经确认的成本方法（移动平均/最近采购成本/固定成本）的统计口径，若未定只能展示“待确认”。
- **任务**：任务指派、计划时间、实际完成时间及逾期是核心；任务状态可以进入企微卡片/H5，但任务**权威源仍在 ERP**，当前不依赖企微内建 Task 产品。
- **权限**：最终企微通讯录/部门为身份参考，但 ERP 业务角色和数据范围要细分销售本人订单/车间本人任务/指定仓库/采购和财务凭证，**组织同步不是自动赋予财务/库存审批权**。

**原生现有页面（GitHub 可直接查）：**

- 简单财务：`financial/MoneyInList.vue`、`MoneyOutList.vue`、`AdvanceInList.vue`、`report/CustomerAccount.vue` 等。
- Java 原生单据/明细：`DepotHead(type/subType/status/linkNumber/organId/tenantId)`、`DepotItem(materialId/depotId/qty/price/linkId/tenantId)`，财务 `AccountHead`，组织 `Organization`、角色 `Role`、客户/供应商 `Supplier`。

**判断**：jshERP 是“进销存 + 轻财务”的可用 Java/Vue 基座，原生组装/拆卸单可借鉴库存变动事务，但代码库**未发现原生正式生产任务、工序、BOM 版本、订单级物料需求与预留、任务分派进度等完整结构**；**不能把组装单当成完整 MRP/MES**。客户端销售订单与采购付款入口存在 ≠ 对应的按订单关联/财务口径和权限已经闭环。相应功能待验证和扩展。

**jshERP 优点**：已在本项目集成 Java + Vue + MySQL + OpenClaw、企微绑定/真实过账/Excel/PDF/图表；中文 UI 与采购/销售/仓库/轻财务已有代码；本仓 `LICENSE` 是 Apache-2.0（最终仍核对上游和所使用组件版本的具体许可）。
**jshERP 缺口**：制造任务/生产工单/BOM 按版管理需要新增域模型、角色审批及 PC 页面；项目级销售交付和轻财务贯穿追踪需要关联设计；是否留在 jshERP 取决于新增域是否保持轻量。

## 5. 备选底座对标（不是立即迁移决定）

| 方案 | 天然优势 | 与现有项目的真实迁移代价 | 适用结论 |
|---|---|---|---|
| **继续 jshERP 定制（当前推荐）** | Java/Vue、中文进销存/轻财务、现有 ERP + Bot 技术集成与实测库存链路可复用；Apache-2.0 仓许可 | 新建订单级 BOM/工单任务/需求/交付的数据模型、PC 页面及库存关联；持续维护定制 | **现阶段优先。** 产品核心只是简化 BOM、任务进度、库存与财务记录时可能总体最快 |
| **ERPNext / Frappe（首要备选）** | 官方 BOM/多级 BOM、Work Order、Job Card、Project/Task、采购销售库存财务与制造天然贯通（docs.frappe.io） | Python/Frappe 技术栈、全新数据库/审批/库存/账号权限/企微网关适配；迁移不能只搬 OpenClaw SOP；许可 GPLv3 需评估 | 如果生产任务、需求计划与 BOM 演变成项目核心，而 jshERP 需大量重造轮子，应启动独立 POC 对标 |
| **Odoo Community/Enterprise（次备选）** | 制造/工位/工单/项目/销售采购库存财务全面，生态广；Odoo 19 文档详述 Work Orders | Python/Odoo ORM/模板重学、中文版和部署本地化、某些能力依不同版本/商业模块而异；Community LGPLv3，Enterprise 需订阅许可 | 不因“功能多”直接切换；只有评估许可/可用模块/实施与本地化总成本后选 |
| **Dolibarr（补充参考）** | BOM/MO/Workstations + 商贸/轻财务/项目模块原生，模块化 | PHP 技术栈与现有 Java 网关差异，GPL-3+ 等发行许可需独立核对，任务细粒度和本地业务流程仍需定制 | 可作轻量对照，不是默认迁移目标 |

## 6. 下一步工作：先定底座，再开发功能（禁止多 Agent 并行）

### Gate 0 — 产品事实固化（已完成文档，不代表客户批准细节）
此文落地根 `AGENTS.md` 与企微 `workspace/AGENTS.md`；Workbuddy 必须暂停将旧 MIX/原料合成设为产品核心。**当前单任务是 ERP 业务差距核查/方案评估，不是 020D 看板或 020B 卡片开发。**

### Gate 1 — 客户真实业务最小闭环/工作量验证
- 选一个真实**生产类订单**样本，从销售报备→销售订单→设计 BOM→缺料/采购→车间任务分派/完成→领料/产成品入库→交付→应收/开票/收款状态，逐节点列现成 PC 页面、服务、数据库表、缺口与是否可直接复用。
- 同时检查耗材/零部件**无需 BOM 直接出库**、服务**只记录**两个最短路径。
- 输出 `docs/architecture/ERP_CAPABILITY_GAP.md`（模块能力矩阵 + 真实源码锚点 + 工作量等级 + 风险）与粗粒度 DB 扩展草案；禁止把 POC 编码已实现假称客户需求已完成。

### Gate 2 — 竞争底座 1 次短 POC（仅当 Gap 证明风险较大）
- 单独用 ERPNext 做同一组制造场景的只读/本地沙盒验证：销售订单→BOM→Work Order/Job Card→采购→领料→完工入库→交付/开票，检查标准 API/可扩展性和改造点；必要时对照 Odoo。
- 比较**二次开发 + 迁移 + 企微集成 + 本地化 + 后续维护**总成本，不使用“模块多”当充分理由。
- 不在原项目并行启动完整迁移，未做选型决定前仍保留现有正常运行的 jshERP Demo。

### Gate 3 — 底座决策再启动核心开发
若保留 jshERP，优先：
1. **业务类型与订单关联主线**（销售订单唯一标识、四类型、责任/交期/状态），附 PC。
2. **生产类订单 BOM 版本 + 轻生产任务**（分派、计划、进度、实际完成、逾期），附 PC；只记录任务完成而非 MES。
3. **需求/库存缺口/采购/领料/成品入库/出库全链路映射**，从真实单据到订单关联可追溯。
4. **交付与财务记录**（客户发票/收款、采购发票/付款、已收未收、延迟/成本报表）。
5. **再接企微组织绑定与 H5、ERP Agent**，复用现有 Bot 通信、授权、图表、PDF，不建第二套事务模型。

## 7. 需要与客户澄清的关键问题（不假定已回答）
1. 一张销售单允许同时包含四种类型的行吗？拆单责任属于销售还是设计？服务订单是否计费开票？
2. BOM 是每订单独立设计还是标准产品模板复用，是否有替代料、版本、生效和损耗？生产是否可以部分完工/返工？
3. 车间任务是固定阶段列表还是灵活任务，是否需要前后依赖、审批、附件、逾期预警及现场工人多人协作？
4. 采购是否允许多个销售订单合并采购、库存预留按订单占用、仓库多人盘点和采购报销归属？
5. 成本统计按采购价、移动平均、还是领料成本；生产人工费用是否计入？订单利润在缺少成本数据时如何展示？
6. 交付是实际物流发货、签收还是项目验收，是否允许多次部分交付？物流负责人做什么？
7. 财务的“记账”最低要求是**票据/付款/回款台账**，还是必须正式借贷记账、税务票面信息/电子发票？
8. 企业微信人员/部门是全员同步还是仅授权员工；跨部门协作销售报备、车间权限与离职权限怎么处理？

### 禁止事项
